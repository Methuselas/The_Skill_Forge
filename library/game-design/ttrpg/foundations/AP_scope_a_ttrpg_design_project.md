# Scope a TTRPG Design Project

## Objective
Turn an initial tabletop role-playing game idea into a bounded project with a chosen rules route, intended players, and delivery commitment. The project is ready to begin when its first deliverable can be made without silently taking on the work of a commercial game line.

## Steps / Flow
1. **Name the experience.** Use **Identify the TTRPG Experience and Design Focus** to state what players should feel and do, then choose the craft area that deserves the project's first attention.
2. **Name the players and delivery context.** Decide whether the work is for a known table, a wider community, or paying strangers. Set its first deliverable before estimating production or promotion.
3. **Choose the rules route.** Apply **Choose Between an Original TTRPG and an Existing System**. Use an existing system when it can carry the intended experience; choose an original system only when its new rules work is necessary.
4. **Branch for obligations.** For an existing system, pause until its permission terms and player expectations are understood. For an original system, write down the rules interaction that needs testing and any special materials players must obtain.
5. **Match the commitment.** Apply **Scale TTRPG Delivery Commitments to Audience and Exposure**. A table-supported prototype may rely on direct facilitation; a public product must communicate its expectations and play procedures without the designer present.
6. **Complete the scope.** Keep a one-paragraph brief naming the experience, audience, rules route, first deliverable, and deferred work. If any line cannot be stated, return to the step that owns it rather than adding features.

## Notes
The protocol prevents an appealing premise from becoming an unbounded promise to design rules, publish a book, build an audience, and run a business all at once. It does not decide whether a project deserves to exist; it makes the obligations of each viable route visible before substantial production work begins.
