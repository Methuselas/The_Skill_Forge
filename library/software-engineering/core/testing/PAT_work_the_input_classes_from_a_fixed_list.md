# Work the Input Classes From a Fixed List, Not From Imagination

## Pattern Rule
**IF** you are choosing what to feed something and the obvious cases are already written
**THEN** walk a fixed taxonomy of input classes rather than continuing to think of examples, because the classes you would think of next are the ones you already thought of
**ELSE** where the input space is large enough that enumerating classes is impractical, generate inputs instead and weight the generation toward realistic sizes.

## Do
- Work the malformed classes as a list: none at all or too little, far too much, the wrong kind entirely, the wrong size, and never initialised. Some will already be covered; the value is in the list being fixed so you are not producing categories under pressure.
- Work the well-formed classes too, which is the half that gets skipped. The ordinary expected case, the smallest legitimate configuration, the largest legitimate configuration, and data produced by the previous version of the system.
- Treat the good-data pass as seriously as the bad-data one. It is easy to believe the normal path is safe because it is the path everyone runs, and a defect on the maximum legitimate configuration is a defect on real customer data.
- Choose values within a class that make checking by hand easy. Any member of an equivalence class is as likely to reveal the fault as any other, so pick the one whose expected answer you can compute without repeating the work under test.
- Count the ratio you end up with. Immature testing writes roughly five confirming cases for every one that tries to break the thing; mature testing runs the reverse, and gets there by writing many more adversarial cases rather than fewer confirming ones.
- Switch to generation when the space is too large to enumerate, and skew the distribution toward the sizes real use produces rather than spreading uniformly across everything legal.

## Don't
- Don't keep brainstorming once the obvious cases are written. Further cases from memory cluster around the same mental model that produced the code, which is the model the defect is hiding in.
- Don't skip the good-data classes as already covered. The nominal case is covered; the minimum and maximum legitimate configurations usually are not, and compatibility with data from an earlier version almost never is.
- Don't pick awkward values to seem thorough. An arbitrary ugly number makes your hand-computed expectation as error-prone as the code you are checking it against, and buys nothing over a clean one from the same class.
- Don't generate uniformly across the legal range and call it realistic. Effort spread evenly lands mostly where users never go.

## Checklist
- Have all five malformed classes been covered — absent, excessive, wrong type, wrong size, uninitialised?
- Have all four well-formed classes — nominal, minimum normal, maximum normal, previous version's data?
- Roughly what is the ratio of adversarial cases to confirming ones here?
- Are the chosen values ones whose expected results you can compute independently?
- If the space is generated rather than enumerated, what shapes the distribution?

## Notes
The reason to reach for a list is that unaided recall is a poor instrument for this specific job. Cases thought of by the person who wrote the code are generated by the same understanding that produced it, so they systematically cluster where that understanding is already sound. The defects live where it is not — and no amount of further thinking from inside that model reaches them. A fixed taxonomy is worth having precisely because it is external and does not vary with what you happen to remember.

The neglect of well-formed classes is the more surprising half and the more expensive one. Adversarial testing gets attention because breaking things feels like testing; the ordinary path feels self-evidently exercised because it runs constantly. But the minimum and maximum legitimate configurations are ordinary paths that rarely occur during development, and data written by a previous version is an ordinary input that developers essentially never have on hand. Faults there reach real users on real data, which is worse than faults reached only by malformed input.

The ratio is the most useful number in this area because it is measurable and it reveals the actual habit rather than the intended one. Groups new to this write about five confirming cases per adversarial one; experienced groups invert that. The inversion is not achieved by writing fewer confirming tests — those still get written — but by producing many times more of the other kind, which is exactly what working a fixed list of classes produces and unaided invention does not.
